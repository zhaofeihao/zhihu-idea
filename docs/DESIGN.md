# 灵感雷达：知乎发现与飞书每日简报

状态：已按方案实现第一版 MVP；下方保留完整设计目标，实际实现范围与待验证项见本节。日期：2026-10-10。

第一版已经实现本地 CLI、Supabase PostgreSQL 表/检查点/预算、知乎官方搜索与可选推荐/回答/热榜、DeepSeek/GPT 两阶段分析、受控关联探索、五类选编、飞书卡片与发送台账、命令反馈、服务器调度和 Docker 配置。测试使用虚构样本、注入 HTTP 和内存 PostgreSQL，尚未使用真实凭据联调。

与完整设计的差异：当前只有指纹和标准化主题短语精确去重，不含语义聚类/关键词相似度；偏好使用近期明确反馈上下文，不自动改权重；成功缓存/任务/成功调用明细仍保留，清理需手动执行；容量自动阈值、自动远端备份、月预算、自动作者追踪、全文补充、卡片反馈尚未实现。服务器按 09:00 中止新增调用并选编完成结果；晚启动仅补当天且最多追加采集 10 分钟。未完成的探索查询暂不保证跨天队列接续。具体命令见 README，真实接口与部署验收见 docs/VALIDATION.md。

## 1. 已确认需求

- 每天从知乎发现值得阅读的内容，包括低热度内容和历史回答。
- 同时覆盖商业灵感、脑洞创意、认知突破、真实故事、交易五类。
- AI 负责筛选、提炼价值和生成简报，支持 DeepSeek 与 GPT 系列。
- 每天发送到专用飞书群，第一版使用自定义机器人 Webhook。
- 优先使用知乎数据开放平台，不把未公开或未核验的接口当成依赖。
- 数据源、分析能力和推送渠道可扩展。
- 存储使用 Supabase Free 托管 PostgreSQL，不部署本地数据库。
- 开发与完善阶段在个人电脑上手动执行；成熟后支持服务器部署与定时执行，两种模式共用业务逻辑。
- 第一版无 Web 阅读界面，无复杂 Agent 框架；先验证每日简报是否值得阅读。

## 3. 官方接口验证是第一道实施检查

知乎官网目录目前列出搜索、热榜、问题推荐、问题回答、用户关注和用户收藏等能力；目录出现不代表账号具有权限，也不代表可以获得任意作者的更新或任意回答全文。

实施时用少量真实请求制作接口能力报告，检查：

1. 搜索返回问题、回答、文章的范围，原文链接、作者、正文/摘要、时间字段和稳定 ID。
2. 分页、排序、时间过滤、结果数量上限、额度与限流表现。
3. 问题推荐和问题回答接口的请求条件、响应内容与访问范围。
4. 用户关注/收藏接口能否作为偏好样本；是否需要独立 OAuth 授权。
5. 热榜是否只提供标题/摘要，以及可否通过已授权接口补充证据。

内容标记 `full_text / excerpt / title_only`。只有标题的候选用于发现，不能直接生成深度结论；摘要内容只做摘要范围内的分析。只有在验证后，才启用全文补充、分页游标或作者追踪。

Access Secret 由服务端环境变量加载；官方鉴权说明使用 Bearer 和秒级 `X-Request-Timestamp`。私有用户能力的授权另行确认。

## 4. 内容发现

### 4.1 五个类别的查询池

每类维护种子问题、关键词、排除词、历史查询效果与最近执行时间。查询内容由配置管理，不能依赖更改代码。

| 类别     | 示例探索方向                                     |
| -------- | ------------------------------------------------ |
| 商业灵感 | 特殊服务、冷门需求、小众商业模式、行业痛点       |
| 脑洞创意 | 不寻常产品设计、有趣假设、跨领域组合、低成本实验 |
| 认知突破 | 反直觉机制、日常现象解释、改变判断的证据         |
| 真实故事 | 特殊职业、一线经历、行业运作、亲历案例           |
| 交易     | 股票、加密货币、套利、ETF、期货、期权、量化、交易复盘与风控 |

系统轮换查询池，兼顾少见表述与专业术语；热榜只占小部分发现额度。历史挖掘不要求平台拥有时间过滤能力，可以从长期查询池中不断发现之前没有见过的内容。

### 4.2 低热度内容的发现

低赞数不作为淘汰条件；热度未知不当作零质量。主要依靠更具体的查询、问题推荐与问题回答能力扩展候选覆盖。搜索接口自身的排序可能偏向热门内容，因此第一版只能验证和改善覆盖，不能承诺遍历知乎或找到所有优质冷门回答。

高质量作者记录为候选兴趣信号；仅在官方接口支持相应查询范围时启用作者跟踪。用户关注 API 不能直接等同于任意作者更新流。

### 4.3 受控的关联探索

AI 可以为优质发现提出 1–3 个后续查询，解释每个查询可能获得什么新信息。调度器验证查询后执行；正文不能直接修改系统指令、任务预算或工具权限。

初始限制：每天最多 5 个探索种子、每个最多 2 个查询、探索深度最多 1 层、合计最多 10 次额外数据调用。实际调用还受全局预算约束。同义查询合并；探索计划跨天保存，额度耗尽后延后执行。

## 5. 筛选与评价

### 5.1 规则与模型分工

规则层先处理重复内容、不可读内容与明确配置的排除项。不能单凭标题、低赞数或短文本判断低质量。

低成本模型初筛输出类别、一个具体发现、通过/拒绝/证据不足以及理由。输出必须按候选 ID 关联，缺失或结构错误进入重试，不自动当成拒绝。每天抽查少量拒绝样本，观察是否错杀冷门但有价值的内容。抽查结果保存供校准，不自动进入简报或关联探索；只有初筛通过的内容有推荐资格。当前编辑偏好优先亲历细节、一线经验、具体案例、失败经验、反常机制和可验证的创意；淘汰缺少实质信息的通稿、宣传、宏观套话和泛泛趋势判断，作者身份仅作辅助线索。

深度分析输出事实依据、评价维度、简报内容与后续查询。可疑的收益承诺、缺乏依据的断言、纯营销或没有实质观察的情绪输出降低推荐优先级；模型置信度不是事实验证结果。

### 5.2 分类别权重

每个维度为 0–100，程序按版本化权重计算总分。模型负责给出维度评价与依据，程序负责计算，避免模型自行生成不一致的总分。

| 类别     | 新颖性 | 启发性 | 商业价值 | 证据充分度 | 内容质量 |
| -------- | -----: | -----: | -------: | ---------: | -------: |
| 商业灵感 |    25% |    30% |      20% |        15% |      10% |
| 脑洞创意 |    35% |    35% |       5% |        10% |      15% |
| 认知突破 |    30% |    35% |       0% |        20% |      15% |
| 真实故事 |    30% |    30% |       5% |        20% |      15% |
| 交易     |    25% |    30% |      10% |        20% |      15% |

2026-10-13 新增 `trading` 交易类别，数据结构与评分规则版本为 `v2`，提示词版本为 `screen-v3` / `analyze-v3`。

2026-10-17 话题改为可自由定义：`discovery.queries` 不再强制配齐内置五类，可只保留关心的话题，每个话题至少 1 条查询、数量不限；话题键为任意字符串（含中文），可直接新增自定义话题。新增可选 `topics` 映射，为每个话题配置展示名 `label`、给模型分类用的含义 `description` 与评分 `weights`（五维整数、和为 100）。未配置 `weights` 的自定义话题默认套用"认知突破"的扫地僧权重，未配置 `label` 回退内置标签或话题键。初筛/分析 schema 的 `category` 按生效话题动态生成，模型只能判定为已配置话题之一，生效话题清单（键/label/description）注入提示词。`limits.brief` 下限由 5 放宽为 1；简报展示名在编排时快照进 `brief.labels`，保证预览/发送稳定。内置五类的权重、提示词与评分版本（`v3` / `screen-v4` / `analyze-v4`）保持不变。

2026-10-16 启用"扫地僧"筛选策略：评分规则升级为 `v3`，提示词升级为 `screen-v4` / `analyze-v4`（数据结构仍为 `v2`，新分析不复用旧规则缓存）。编辑偏好改为优先一线/民间、看似平凡却给出意外、颠覆直觉、读完"大为震撼/原来如此"的具体洞见；要求存在一个"震撼点"。五类权重整体抬高新颖性与启发性（见上表），让意外与震撼主导类别内排序；证据充分度与内容质量下调，但仍作为选编硬门槛（`quality ≥ 50`、`evidence ≥ minEvidence`）。提示词显式打压学术腔、官方腔、报告体、权威总结与面面俱到的科普综述：即便严谨、引用充分、术语专业，若缺少意外的一手洞见也降权或拒绝，宁可朴素口语也不要正确但无感的通稿式行文。配套将默认 `selection.minEvidence` 由 45 下调为 40，给缺少正式引用的一手经验留出空间；查询池改为偏向民间高手、行业潜规则、颠覆认知与失败复盘。交易内容侧重具体机制、执行成本、风险约束和失败复盘；商业价值评价机制的实际用途，不评价宣称收益。仅有喊单、荐股荐币、收益截图、带单宣传或无依据预测的内容在初筛拒绝；历史盈利、回测或作者自述不能证明当前存在可复制的盈利机会，套利不能被描述为无风险。查询池支持扩展，默认参与五类轮换。

新颖性分开记录“少见的视角”和“对用户是否新鲜”。前者不宣称证明原创，后者基于用户已收到内容和明确反馈估计。虚构假设可以获得高创意分，但必须标注假设，不能作为真实案例推送。

初始分数用于类别内排序，不解释为客观真理。推荐门槛、证据要求和不同类别的分数尺度通过样本校准后确定。

### 5.3 简报选编

先过滤证据不足及低质量内容，再在类别内排序，按质量、主题多样性与历史新鲜度选编。先去除原文重复，再合并表达同一发现的内容，避免同一个商业案例每天被不同帖子重复推荐。

第一版使用内容 ID、规范化 URL、正文指纹和关键词相似性；语义去重作为可替换接口，后续根据实际重复率决定是否加入 embedding。不会承诺第一版可以识别所有语义重复。

## 6. 简报格式

默认是一份每日简报，根据卡片大小可分成带编号的多条消息。日期使用北京时间；历史内容标注原文时间，来源未给时间则标注未知。

每条内容包含：

- 类别与简洁标题。
- 核心发现：原文具体讲了什么，约 80–120 字。
- 推荐理由：哪些信息或视角值得花时间阅读，约 40–80 字。
- AI 延伸：可选的一个启发或可尝试的问题，明确标为 AI 推演。
- 作者、原文链接、发表时间（若接口提供）、证据范围。

原文 URL 和作者从数据库字段填入，不由模型编造。原文观点、个人经历、未经核验的说法与 AI 推演分别标注。默认不展示精确评分；分数及筛选理由保存在后台，方便调参。

简报顶部显示当天条数、覆盖类别与大致阅读量，不展示对阅读决策没有帮助的内部 token/接口细节。

## 7. 飞书推送与反馈边界

已确认：专用群 + 自定义机器人 Webhook。服务只向配置好的目标发送简报，不创建群，不通知其他用户。

机器人安全配置支持签名校验时按官方文档实现，Webhook 和签名密钥仅在服务端保存。发送前验证卡片结构与字节大小，过长则按条目分拆。HTTP 成功和飞书业务返回成功分别检查。

每日简报与每个分片先写入发送记录，记录内容快照、状态和尝试次数。确定未发送的失败可以有限重试；请求超时属于结果不确定，不能宣称 Webhook 具备严格 exactly-once。该状态保留为 `unknown`，第一版不自动重复发送，人工确认后可重发。分片失败只处理对应分片。

自定义机器人 Webhook 作为单向推送入口，不假设它能直接处理“有意思/一般/不感兴趣”的回调。因此：

- 第一版提供通过命令或导入记录的反馈，简报为条目保留稳定短编号。
- 飞书消息的反应、原文点击不自动视为已接入反馈或阅读信号。
- 若需要卡片内直接评价，后续接入飞书自建应用及卡片回调；或提供经过身份校验的极小反馈页面。这两种都不等于开发完整阅读网站。

没有反馈时按初始规则运行，不能宣称已经学习用户兴趣。收到反馈后，定期生成待审阅的偏好建议，保留明确喜欢与不喜欢的理由；调整幅度受限，五类覆盖与探索额度不被自动取消。

## 8. 技术架构与模块

建议 TypeScript + Supabase Free 托管 PostgreSQL + 可独立执行的任务 runner。开发期用 CLI 在个人电脑手动运行，服务器阶段用同一个 runner 和 Docker 镜像，由调度服务触发。数据库不存本地，任务、分析结果和发送记录均写入 Supabase。具体调度时间显式指定 Asia/Shanghai。第一版不需要 React、Redis 或复杂 Agent 运行时。

### 8.1 Supabase 免费存储方案

2026-10-10 核对官方价格页：Free 每项目数据库额度 500 MB，文件存储 1 GB，包含 5 GB 出站流量和 5 GB 缓存出站流量；最多 2 个活跃免费项目，闲置 1 周后会暂停，免费套餐不包含自动数据库备份。数据库额度与文件存储额度独立，不能把 1 GB 文件额度算成数据库容量。额度可能调整，以控制台及官方价格页为准。

该规模适合个人 MVP，但不适合无限期保存所有候选全文。初始保留策略建议：

| 数据                       | 保留策略                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 未入选候选的正文或原始响应 | 最多 30 天，之后清理大字段；单独保存可抽查的代表样本                                       |
| 已入选内容                 | 长期保留标题、作者、原文链接、提炼结果与关键证据摘录；大段原文默认保留 90 天               |
| 去重记录                   | 保留精简的外部 ID/URL 指纹与内容指纹，减少旧内容重复发现；容量不足时按配置压缩历史覆盖范围 |
| 已完成任务和详细调用日志   | 明细 30 天，费用与运行统计按日汇总长期保留                                                 |
| 简报、反馈与用户偏好       | 长期保留，纳入总体容量监测                                                                 |

估算示例：每天 200 条去重后的候选、每条原文平均 20 KB，30 天约 120 MB；这是未计压缩、表/索引、分析和其他数据的粗估，实际使用样本与数据库报告测量。第一版不保存图片文件、完整重复响应或全量向量索引。

建议数据库总量达到 350 MB 时提示并触发按已配置保留期限的清理计划；400 MB 时限制新增大文本。以上为应用阈值，不是 Supabase 官方配额。清理只作用于符合保留策略的记录，不删除长期保存的精选、反馈或运行中的任务。删除后空间占用不一定立即下降，需要检查 PostgreSQL vacuum 与实际数据库报告，不能单靠删除行判断已腾出容量。

worker 使用标准 PostgreSQL 客户端和服务端 `DATABASE_URL`，连接池保持较小。常驻 IPv6 后端可直接连接；IPv4-only 部署使用 Supabase Session pooler；未来 serverless 则采用 Transaction pooler 并按客户端要求处理预编译语句和会话状态限制。连接字符串从项目 Connect 面板获取，使用 TLS，不自行拼接地址。第一版此路径不要求 Supabase API key。

业务表放在不对 Data API 暴露的 schema，使用专用数据库角色授权；后续如需浏览器访问再接入 Auth/RLS。Supabase 仅承担存储，不能因此认为采集进程已托管：电脑关闭时仍能运行的每日任务需要另行部署 worker 或安排适合的云任务执行环境。

免费套餐的暂停行为需纳入任务失败与人工恢复处理；正常每日业务会产生实际使用，但不承诺免费服务永不暂停。备份建议定期导出到非本地、私有的对象存储；若使用 Supabase Storage，则与 1 GB 文件额度共同核算并轮换旧备份。备份导出和恢复需要单独验证，不能把“数据在云上”等同于“已有自动备份”。当前仅制定策略，没有创建 Supabase 项目、执行清理或启用备份。

### 8.2 本地手动执行与服务器部署

运行模式由入口决定，业务流水线只有一份：`CLI / scheduler → runner → pipeline → Supabase / providers / Feishu`。本地和服务器不维护两套采集、筛选或推送实现，也不依赖电脑上的数据库、文件检查点或固定路径。

以下命令现已实现，真实模式需要先配置环境与显式迁移；没有密钥时仅 demo 可完成离线运行：

| 入口                               | 设计行为                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `npm run run`                      | 手动完成采集、分析、选编，显示简报预览；会使用真实配置的知乎/模型 API，并将状态写入 Supabase，默认不发送飞书 |
| `npm run run -- --send`            | 手动完成上述任务并发送到配置好的飞书群，发送后正常退出                                                       |
| `npm run run -- --stage=discover`  | 只执行发现阶段，便于检查 API 与查询效果                                                                      |
| `npm run run -- --resume=<run-id>` | 恢复该次运行尚未完成的阶段，复用已成功的结果                                                                 |
| `npm run preview`                  | 从 Supabase 读取已有简报并预览，不重新采集、调用模型或发送                                                   |
| `npm run demo`                     | 使用仓库内样本和内存状态验证流水线，无需数据库和 API 密钥；不代表持久化任务已运行                            |
| `npm run service`                  | 常驻调度与执行服务，用于服务器；按配置的北京时间执行采集与发送                                               |

本地手动任务按执行时刻运行，不受 07:00/09:00 的服务器时刻限制，下午也可运行并立即发送。一次任务正常结束后释放连接并退出，不要求保持终端或浏览器打开。开发期调度默认关闭，调整代码不会自动重跑付费任务或重复发送。

任务支持小批量覆盖，例如 `--limit=20`，并可按类别或流水线阶段执行。启动时按该模式检查必需配置：预览已有结果仅需要数据库，采集需要知乎密钥，分析需要所选模型密钥，发送需要飞书 Webhook；缺失时输出明确错误。终端显示阶段进度、候选数量、估算用量、run ID 和错误。失败返回非零退出码，成功和没有合格内容正常退出。

手动模式和服务模式共用 Supabase 中的检查点、分析缓存、简报快照、发送记录与预算。中断时尽量保存当前状态；强制退出后通过任务租约过期恢复。重跑同一逻辑周期复用成功阶段；已发送的简报默认不重复发送。如需同日新增采集或按新提示词重分析，显式创建新运行版本，并显示可能新增的模型用量；重发既有简报使用独立发送入口，不重新分析。

迁移服务器时安装同一版本程序或镜像，配置相同 Supabase 连接串和 API 密钥，再启动 `service`。不需要把本地数据库迁往服务器。已有精选、偏好、任务状态和发送记录可继续使用。开发期间已有的预览文件不是业务状态来源，不要求复制。

服务器交付规划包含 `Dockerfile`、不含本地数据库容器的 Compose 配置、环境变量示例、部署/升级/恢复说明。服务器既可单次执行，也可常驻调度；常驻模式输出标准日志、提供进程健康检查并支持优雅退出。数据库租约和周期唯一标识控制跨主机竞争，避免本地与服务器同时操作同一任务；部署后开发默认使用样本或单独的运行命名空间，减少对正式简报的影响。

服务器调度、数据保留清理和备份均需显式启用；本地手动模式不会因启动一次任务就在后台常驻。开发期连续一周没有实际数据库使用时，免费项目可能暂停，恢复后再手动运行，暂不为避免暂停另建无人值守任务。

早前初始化遗留的 Eve 模板文件仍保留在 agent/，当前入口已迁移为 src/cli.ts，构建与运行不依赖 Eve。

```text
本地 CLI / 服务器调度器
      ↓
任务数据库 → worker → 数据源适配器 → 统一内容存储
                ↓
          初筛 → 深度分析 → 点子归组 → 简报选编
                ↓                    ↓
          分析与用量记录        发送记录 → 飞书适配器
                ↑
            用户反馈
```

核心接口的职责：

| 模块            | 输入 / 输出                           | 扩展例子                       |
| --------------- | ------------------------------------- | ------------------------------ |
| SourceAdapter   | 查询计划 → 规范化内容、游标、来源能力 | 知乎、Reddit、HN、RSS          |
| ModelProvider   | 任务、模型配置、结构要求 → 结果、用量 | DeepSeek、OpenAI、其他兼容服务 |
| Analyzer        | 内容与评价规则 → 分析结果             | 筛选、价值提炼、事实核验、聚类 |
| BriefComposer   | 合格分析结果与历史推送 → 简报快照     | 日报、周报、专题               |
| DeliveryAdapter | 简报分片 → 发送结果                   | 飞书 Webhook、飞书应用、邮件   |

公共模型不依赖知乎字段、飞书卡片 JSON 或特定模型响应。每个源声明实际支持的能力；某个源没有全文或时间字段时，分析层按证据范围工作。

建议目录：`src/domain`、`src/sources/zhihu`、`src/models`、`src/pipeline`、`src/delivery/feishu`、`src/storage`、`src/jobs`、`src/cli`、`config`、`prompts`、`tests/fixtures`。

## 9. 持久化与任务可靠性

主要数据对象：

| 对象                   | 核心字段 / 用途                                               |
| ---------------------- | ------------------------------------------------------------- |
| content_items          | 来源、外部 ID、URL、作者、文本、证据范围、发表/发现时间、指纹 |
| discovery_queries      | 查询、来源、类别、父探索种子、执行时间与效果                  |
| discovery_hits         | 查询与内容的关系，避免丢失发现路径                            |
| analyses               | 内容指纹、任务阶段、模型、提示词/规则版本、维度分、理由、产物 |
| idea_clusters          | 同一发现的多个来源；合并理由与方法                            |
| briefs / brief_items   | 日期、收件目标、选中内容、固定简报快照                        |
| deliveries             | 分片 ID、发送状态、错误、尝试次数                             |
| feedback / preferences | 用户评价、原因、偏好版本                                      |
| jobs / usage_events    | 任务状态、租约、检查点、API 调用数、token 与成本估算          |

任务状态为 `pending / running / succeeded / failed`，租约过期可恢复。使用数据库唯一约束避免同一内容版本与分析版本重复处理；简报以日期、目标、运行命名空间和配置版本标识，普通重跑优先复用已有快照。逻辑周期与租约由数据库协调，不以本地进程 ID 或电脑文件锁作为唯一依据。

任务并发有上限；临时失败指数退避，鉴权失败不反复重试。超时或失败保留错误信息而不回滚已完成分析。服务器定时模式每天收集截止时刻的可用结果，晚到结果留待下次；手动模式则在本次运行结束后选编。服务器漏跑时补当前周期，不连续刷屏补发多天简报。

不让 HTTP 页面请求承担整条采集流水线。未来扩容可以替换任务执行器为队列，核心分析与推送接口保持不变。

## 10. 模型配置与成本

每个任务阶段独立指定 `provider / model / baseURL / timeout / outputLimit`，支持 DeepSeek 和 OpenAI 官方接入。模型 ID 通过配置提供，开发时查询当前可用型号，不固定过时型号。

低成本模型可完成全部阶段；更强 GPT 用于复核为可选项。跨提供商 fallback 默认不开启，避免在未配置的账号上产生费用。模型失败不会悄悄变成高价模型调用。

控制方式：先去重、限制文本及输出、同一内容/模型/提示词版本缓存结果、限制深度分析数量、限制探索调用。模型输出按 schema 验证，文本中的指令当作来源数据处理。

成本分别核算知乎调用和模型用量：

```text
模型估算费用 = Σ(实际输入 token × 输入单价 + 实际输出 token × 输出单价)
总估算费用 = 模型估算费用 + 已知知乎付费调用估算
```

单价、币种、缓存计费项和生效日期可更新；缺少价格时显示未知，不估成免费。开发阶段用样本测算，之后设定每日/每月预算。执行前预留预计消耗，并把并发调用计入，避免只在花费发生后检查额度。供应商最终账单为实际费用依据。

## 11. 第一版验收

1. 真实知乎样本能力报告完成，文档未证实的能力没有被当作已实现功能。
2. 离线模式可从样本完成发现、筛选、选编与飞书消息预览，不调用付费服务或发送消息。
3. 少量真实请求验证 DeepSeek 和 GPT 的结构化输出、失败行为与用量记录。
4. 用人工标注的小样本比较五类推荐结果，检查无商业价值的优质脑洞不被统一权重错杀。
5. 每条简报内容可追溯；模型建议与来源描述有明确区分；没有可用证据时不编造正文。
6. 重跑不会重复分析；中途重启可以恢复；确定失败和发送结果未知有不同处理方式。
7. 超出探索或成本预算时停止新增调用，已完成内容仍可生成简报。
8. 显式配置群 Webhook 后验证真实飞书卡片；默认命令为预览，实际发送使用明确发送入口。
9. 部署到常在线机器后验证北京时间调度；配置文件本身不代表任务已经在每天执行。
10. 本地单次运行无需常驻服务、浏览器或本地数据库；默认预览与显式发送的行为清楚可区分。
11. 本地中断后可使用同一 run ID 恢复；服务器使用同一 Supabase 时可以接续，已成功分析和已发送简报不会因切换机器重复执行。
12. Docker 服务入口与本地 CLI 调用同一流水线；开发模式不会自动启动服务器定时任务。

两周观察：实际推荐条数、主动反馈的“有意思”比例、拒绝样本中的漏筛、重复主题率、类别覆盖、低热度及历史来源占比（字段可用时）、每日实际费用和发送成功率。没有点击或阅读遥测时，不把它们伪装成已测量指标。

## 12. 实施顺序和所需配置

先接口验证与样本评估 → 统一数据模型与 Supabase 存储 → 本地 CLI 与初筛/深度分析 → 简报预览 → 手动飞书发送 → 开发期持续调优 → 服务器部署与定时执行。

开始联调时需要：

- `ZHIHU_ACCESS_SECRET`。
- `DEEPSEEK_API_KEY` 与/或 `OPENAI_API_KEY`，以及要使用的模型 ID。
- `FEISHU_WEBHOOK_URL`，启用签名时增加 `FEISHU_SIGNING_SECRET`。
- `DATABASE_URL`：Supabase 项目 Connect 面板的 PostgreSQL/Session pooler 连接串，含数据库密码，仅存于服务端环境配置。第一版不要求额外 Supabase API key。

09:00、条目上限和阶段处理量均可配置；09:00 只约束服务器定时模式。开发期不要求先准备服务器，先确定每次/每日 API 预算；成熟后再配置常在线服务器。密钥写入本地未跟踪的环境配置或服务器 secret，不写入源码、文档或日志。
